# CALS Ad Tech: Technology Stack

Compiled on 26 Oct 2026 from the Confluence space **Converged Advertising & Linear Systems (CALS)** (`PAYTV`) on `wbdprod.atlassian.net`, plus one Jira ticket.

## Summary

CALS Ad Tech is built on AWS:

- **Services:** ECS with Terragrunt.
- **Data:** Managed Airflow (MWAA) with Apache Iceberg.
- **Monitoring:** OpenSearch and Prometheus.
- **Sign-in:** Cognito with Okta.

On top of that sit business systems such as iDeal, Rassilon, Salesforce, Operative and FreeWheel. Parts that are designed but not live yet are marked as such.

There is no single official "tech stack" page; this document combines the sources listed at the end.

---

## 1. Cloud platform and infrastructure (Flamingo / `cals-platform`)

CALS Platform Engineering (Flamingo) is a shared AWS platform for Ad Sales services. A team that joins it gets networking, ingress, deployment identity, CI/CD, authentication and monitoring without building them itself.

### Platform repositories

- **`cals-project-scaffolding`:** a generator that runs as a command-line tool and as an MCP server (`cals-scaffold`). It holds templates for every supported runtime, the ownership metadata (OMD) contract, and the resolver that connects a repo to the platform's accounts and clusters.
- **`cals-platform`:** the Terragrunt live tree. It owns the shared VPC, ECS cluster, ingress, ECR, deployment IAM, the tenant registry and the published catalog.
- **`cals-common-git-workflows`:** reusable GitHub Actions workflows for build, test, image publish, database migration, deployment and Terragrunt plan/apply. Every repo uses them at the floating `@v1` tag.
- **`cals-identity-service`:** Cognito, Okta federation and the shared login back end (BFF).
- **`cals-devops`:** Terraform stacks for central OpenSearch, the log pipeline, Amazon Managed Prometheus and the OpenSearch UI.

### Core technologies

- **Cloud:** AWS. Non-prod runs in `eu-west-1` and `us-east-1`; prod runs in `eu-west-1`.
- **Infrastructure as code:** Terragrunt (`cals-platform`, `carl-infra`) and plain Terraform (`cals-devops`, `carl-infra-modules`).
- **Compute:** a shared ECS cluster using Fargate and EC2, with ECS Service Connect between services, and Lambda for the login back end.
- **Networking and entry point:** a shared VPC with subnets, NAT and VPC endpoints, plus an Application Load Balancer, API Gateway, VPC Link, wildcard DNS and TLS.
- **Containers:** Docker images stored in Amazon ECR.
- **Configuration:** non-prod reads live network settings (VPC and subnet IDs, monitoring endpoints) from SSM Parameter Store at apply time. Prod pins them instead.
- **Service templates:** generated by `cals-scaffold`. Spring Boot is the confirmed runtime.
- **Ownership metadata:** every repo carries `.omd/now.yaml` files. Their values become `cals_omd_*` tags on AWS resources, container environment variables, metric labels and log fields.
- **Catalog:** `catalog.yaml` is published under the git tag `v1`. It carries account IDs, state backends, cluster names and ingress settings, so no team hardcodes them.
- **Flamingo:** turns a product requirements doc into a platform-aware plan using spec-driven tooling (Speckit). It is **in test**.

## 2. CI/CD and source control

- **Source control:** GitHub, in the `discoveryinc-dci`, `turnercode` and `warnermediacode` organisations.
- **Pipelines:** reusable GitHub Actions workflows (`cals-common-git-workflows` at `@v1`).
- **Makefile contract:** every repo implements the same make targets (`lint`, `unit-test`, `functional-test`, `build`, `docker-build`, `docker-publish`, `migrate`, `omd-service`). The shared workflows call only these targets, so one CI fix reaches every repo at once.
- **AWS access from pipelines:** GitHub OIDC into a pair of roles per service, `cals-<service>-deploy-plan` (read-only) and `cals-<service>-deploy-apply` (scoped write). There are no static AWS keys.
- **Infrastructure layers:** each service splits its infrastructure into two layers. The `infra/infra/` layer is applied once and rarely changed. The `infra/deploy/` layer is applied on every release.
- **Deploy time:** about 6 minutes end to end, measured for a Spring Boot service.
- **CARL workflow:** environments go dev, then qa, then stage, then prod. Every PR needs one approval and passing CI, and branches are named after the Jira ticket key (for example `CARL-123`).

## 3. Identity and sign-in (`cals-identity-service`)

- A central AWS Cognito user pool, linked to WBD Okta. This is live in `development`.
- Each service gets its own Cognito app client.
- One shared login back end (BFF Lambda image) that every service deploys. `cals-neo` is the first to use it.
- AWS Identity Center SSO for the OpenSearch UI and AWS accounts.
- Okta SAML for the Iceberg data accounts.
- AppCentral for most AWS access requests.

## 4. Monitoring (`cals-devops`)

Monitoring runs in its own AWS accounts. A service only needs to write JSON logs to stdout and expose a Prometheus endpoint. Onboarding needs no manual index setup, because routing is based on the `cals_omd_*` fields.

### Logs

1. The application writes JSON to stdout.
2. A Fluent Bit sidecar (FireLens) adds the `cals_omd_*` fields to each record.
3. Fluent Bit writes to Kinesis Data Streams in the central account (on-demand mode, 72-hour retention, encrypted with KMS).
4. OpenSearch Ingestion (Data Prepper) writes each record to OpenSearch 3.5.
5. Each service gets its own daily index, named `cals-logs-<env>-<service>-YYYY-MM-DD`. Records without the `cals_omd_*` fields go to a separate `unassigned` index.
6. Records that fail to ingest go to an S3 dead-letter bucket.

An older Firehose log path is still running in parallel.

### Metrics

- An OpenTelemetry Collector (`otel/opentelemetry-collector-contrib`) sends metrics to Amazon Managed Prometheus, authenticated with SigV4.
- Prometheus keeps metrics for 150 days in non-prod and 365 days in prod.

### Viewing, access and alarms

- The OpenSearch UI shows logs and metrics in one place. Metrics come through the `cals_metrics` data source and are queried with PromQL.
- Access is through AWS Identity Center SSO.
- CloudWatch alarms cover the ingestion path and notify through SNS.
- A setup Lambda configures OpenSearch access control and deletes logs after 30 days.

### Cluster sizing

- **Non-prod:** 3 × `r8g.large.search` data nodes and 3 × `m7g.large.search` dedicated master nodes, with 100 GB of gp3 storage.
- **Prod:** 3 × `r8g.xlarge.search` data nodes and 3 × `m7g.large.search` dedicated master nodes, with 500 GB of gp3 storage.

### Not built yet

- **Tracing:** the collector accepts traces and discards them.
- **Metric alerting:** Prometheus alert rules and Alertmanager are disabled.
- **Lambda logs:** Lambda functions log to CloudWatch and don't reach the central log pipeline.

## 5. Data and analytics platform (CARL: Centralized Analytics & Reporting Landscape)

- **Cloud:** AWS.
- **Orchestration:** MWAA (Amazon Managed Workflows for Apache Airflow).
- **Data lake:** Apache Iceberg tables on S3.
- **Catalog and governance:** AWS Glue Catalog (Glue REST Catalog) with Lake Formation.
- **Processing:** AWS Glue jobs.
- **Data layers:** landing, then bronze (raw), silver (cleaned) and gold (curated).
- **Reporting:** AWS Quick, with a separate semantic layer (`carl-semantic-layer`) that defines metrics independently of the reporting tool.
- **Deployment:** GitHub Actions deploys to S3 and MWAA. Infrastructure is applied with Terragrunt.
- **Compliance:** SOX and GDPR controls, lineage tracking and fine-grained access control.
- **AI plans:** natural-language querying, an agentic AI framework, knowledge graphs, and anomaly detection.
- **Legacy tools being replaced:** Crystal Reports, MicroStrategy, Looker, Tableau and Snowflake.

### CARL repositories

- **`carl-data-engineering`:** data pipelines, MWAA DAGs and Glue jobs.
- **`carl-infra`:** infrastructure (Terragrunt/Terraform, MWAA environments).
- **`carl-infra-modules`:** shared Terraform modules.
- **`carl-semantic-layer`:** semantic layer and analytics definitions.
- **`carl-legacy-source`:** legacy code bases, such as Looker.

## 6. Inflight Ad Optimization Engine (ADD 009, linear)

- **Solver:** Gurobi MILP. The open-source CBC solver was rejected because it was too slow at scale.
- **Solver compute:** ECS on EC2, with a Gurobi Compute Server handing out licenses. ECS Fargate was considered and kept as a fallback.
- **Orchestration:** MWAA DAGs, chosen over AWS Step Functions. Long waits use deferrable `EcsRunTaskOperator` tasks, and an `EventPollerTrigger` handles event-driven runs.
- **Run tracking:** a DynamoDB run registry, with per-network locking done through conditional writes.
- **Validation findings and configuration:** Aurora PostgreSQL (Multi-AZ).
- **Run archive and audit:** S3.
- **Data access:** an API Gateway layer over Rassilon and iDeal.
- **Forecast inputs:** Star Estimator now; Snowflake Linear Forecasting is planned.
- **Events:** a change feed from the source system now. Kinesis or MSK would only be added if event volume grows.
- **Language:** Python.
- **Still open:** the UI stack (React with Amplify is one option), and how outputs are measured (Nielsen, VideoAmp, Comscore).

## 7. Composable OMS (CoMS) order creation (ATM-1578, draft)

- **API:** a single REST endpoint, `POST /v1/orders`, that takes an `order_type` field (`LINEAR_DDL`, `LINEAR_NATIONAL`, `DIGITAL` or `DR`).
- **Validation:** a configurable rules engine, so rules change without a redeploy.
- **Persistence:** one transaction writes the full Deal → Order → Line → Unit hierarchy.
- **Events:** publishes `order.created` using an outbox pattern. Whether that runs on EventBridge or MSK is still open.
- **Existing services:** the current Unified Media Planner (UMP) services run behind API Gateway, are written in TypeScript, and expose Swagger docs.
- **Still open:** how callers authenticate (API keys, mTLS or Cognito client credentials).

## 8. Ad tech business systems

### Orders and CRM

- **Salesforce:** CRM, opportunities, digital orders and affiliate CRM.
- **iDeal:** linear orders, inventory and invoicing.
- **Operative:** digital order execution.
- **Neo / Metropolis:** CRM intent and selling.

### Trafficking and ad serving

- **Rassilon:** linear trafficking and broadcast log editing. Built with SolidJS, Rust/WASM, Spring Boot and Oracle PL/SQL.
- **FreeWheel:** digital ad serving and trafficking.
- **Gabriel / MSA:** where the broadcast log lives, plus EDI.
- **Aries:** playout.

### Scheduling

- **Broadview:** US.
- **MediaGenix:** international.

### Measurement and attribution

- VideoAmp, Nielsen, Comscore, iSpot, EDO and LoopMe.

### Planning and reporting tools

- Unified Media Planner (UMP), PAM, Stewardship and the Account Budgeting System (ABS).

### Affiliate systems

- AMS, AMS GRS, DORS, Millennium, SMARTer, CHARM, Sage, iBravo, AFS and Pasarela.

### Other

- **VPPA ad proxy:** a privacy-compliant proxy that sits in front of FreeWheel. Its Confluence page has no implementation details.
- **AWS Bedrock AgentCore:** AI for the Commercial Clearance tool intake.
